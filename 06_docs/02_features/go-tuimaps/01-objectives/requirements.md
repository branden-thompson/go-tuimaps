| FR-11 ▲ | Simplify host shapes to the dot tolerance of the view. Shapes outside the view cost nothing to draw, and nothing is ever drawn outside the given rectangle. The simplified, *unclipped* result is cached per zoom bucket (buckets defined in PLAN; fractional zoom maps to one); on a miss, the nearest cached bucket is drawn while the right one is prepared, so a shape never vanishes mid-zoom. Simplification is iterative, never recursive; its worst-case bound is stated with the algorithm PLAN chooses — n·log n is a target, not a choice of algorithm. **Host geometry is borrowed, not copied:** the host must not change it while the overlay is set, and replaces it by setting the overlay again. **The borrow ends only when the library says so:** cancellation is cooperative, so a simplification or description job may still be reading the old geometry for a moment after it is replaced; the replace and remove calls therefore report when no library job still reads it, and the host must not reuse the old memory before then. Documented, and covered by a race-detector test that reuses the memory at once and must fail. Borrowed bytes count against the *vertex* cap (NFR-20) only; bytes the library owns — simplified forms, indexes — count against the shape cache's byte cap. Where a bucket's simplified form would exceed a quarter of that cap (default), the library draws from the borrowed geometry instead of caching it — culled by runs of segments, not only by whole rings, since one very large ring is never culled whole; split at ±180° as it is drawn; and **held to a time bound of its own**, tested at the zoom-12 worst-case view, with the figure set at PLAN exit beside NFR-3's. | **Colour and theme** | | |
| FR-15 ▲ | Take a host palette covering basemap roles and overlay ramps (temperature's scale excepted — D-55, D-62); apply changes at runtime without re-parsing tiles; expose a change counter. **The palette is a documented contract of semantic tokens (D-63):** every colour a host can set has a stable, named role — basemap roles, and each overlay's ramp steps named by meaning (an intensity class, a severity), never by position; a generic grid's ramp, whose classes are the host's own, is tokenised by anchors — low, middle, high — and interpolated — so a host can map its theme onto the tokens, or build a colour-vision-safe theme of its own, without reading the source. | FR-16 ▲ | Keep every ramp — default or supplied by a theme — **ordered** (relative luminance changes in one direction along the ramp, or on each side of a labelled midpoint for a diverging ramp), **distinct** (each step maps to a different palette entry at the colour depth in use) and **readable** (line work and glyphs at least 3:1, labels and legend text at least 4.5:1, against every cell background they are drawn on, by the WCAG formula). **The foreground is chosen per cell by computing both candidates' contrast and taking the higher** — not by a brightness threshold, which picks the worse candidate on some steps. **An area tint is never a shape's only edge:** a polygon's outline meets 3:1 against every background it crosses, the painted ground included, and is not optional. A checker reports each violation; a host can run it in its own tests. **Colour-vision safety (D-53):** every *default* ramp, **at every colour depth the release supports**, keeps adjacent steps distinguishable under simulated protanopia, deuteranopia and tritanopia (threshold confirmed in PLAN); a *themed* ramp is run through the same checker and violations are reported, not refused. *The re-coloured radar ramp in the specimens fails this at 256 colours; a passing ramp is owed in PLAN. A person can reach the safe defaults wherever the host exposes the setting, which the README asks every host to do (FR-15, NFR-20, D-63).* **Temperature is not themeable (D-55):** it always uses the library's colour-vision-safe diverging ramp; a theme may adjust its line work and labels, not its bands. **The scale is absolute (D-62):** for a temperature grid the library owns the colours, the midpoint — freezing, 0 °C or 32 °F — and the class breaks, so one colour means one temperature in every host on every day — breaks are defined once, in °C, and converted exactly for °F, so this holds in either unit; the ramp is longer than the seven steps of specimen 16 and draws on established weather-map scales, subject to the colour-vision rule above at every depth (*specimen and checker results owed in PLAN*). **Kinds are a closed, library-owned set:** *generic* (the default) and *temperature* with its unit; an unknown kind, or a ramp or breaks supplied with a temperature grid, is a typed error. This is a convention, not a control: a host that declares its temperatures generic can colour them as it likes. Every other overlay's ramp stays themeable. Legend swatches show the ramp actually drawn, with text chosen by the same contrast rule. | D-36, D-53, D-55, D-62, S1-3, S10-2, A-3, A-4, CQ-14, R2-AX |

## Non-functional requirements

| ID | Requirement | From |
|---|---|---|
| NFR-1 | Pure Go: the library, the app and every dependency build with CGO off, enforced by a cross-compile for macOS (arm64, amd64), Linux (amd64, arm64) and Windows (amd64). | D-22 |
| NFR-2 | Declare a Go version no newer than the first host's (1.25). | T-B, D-19 |
| NFR-3 ▲ | **Target (D-29): 8 MB.** Measured reproducibly against a **pinned fixture** committed to the repository. **The fixture (D-48):** one regional view; an alert overlay of 10 zone shapes, about 50,000 vertices; one single-frame radar image; one temperature grid — *its exact tiles, vertex count, image and grid dimensions are fixed in PLAN, and named in the test.* **Live** = the change in the runtime's live-heap metric after a forced collection, taken after a scripted tour that fills every cache to its cap — not after a first view. **Peak** = the maximum change in the runtime's heap-objects metric, sampled every 10 ms in a standalone harness, at the default collector setting. **Pass (as ruled, D-48):** live ≤ 4 MB, peak ≤ 8 MB. Default cache caps plus fixed buffers together ≤ 3 MB, leaving 1 MB for all other live state. Measured with one instance, and again with three sharing caches, as the first host plans (FR-27). **A tension the measurement must report, not hide:** at the default collector setting the heap-objects metric runs to about twice live through garbage alone, so at live = 4 MB the peak line is reached with no room for transients; in practice live must sit nearer 3 MB. PLAN's measurement reports both figures, and any change to the ruled lines is HUM LEAD's. **These lines apply to the fixture.** For extreme or hostile input the bound is a stated formula, not 8 MB: per tile in decode, body cap + decompressed cap + retained cap (NFR-10), times the decode concurrency, which drops to one for any tile over the measured maxima; a decoded tile larger than a quarter of the tile cache is drawn and not cached. The host's resident-memory protocol is confirmatory only, because its own run-to-run spread (8.5 MB) exceeds the figure being measured — *a change from the "added resident memory" D-29 named; HUM LEAD was told of it when D-48 was put, and the options file records the wording.* The embedded tiles (1.7 MB) are program data: invisible to heap metrics and present in the host's resident memory; stated here so it is not a surprise. Every cache — memory **and disk** — is capped by bytes with host-set caps. **Worst case, tested separately, at two named views (the fixture view and zoom 12):** a 58-zone, 812,058-vertex alert is accepted and drawn without the library copying the source geometry; library-owned bytes stay within the shape cache's cap by FR-11's rule; growth is bounded. Validated or revised at PLAN exit by measurement. | D-29, D-48, CQ-2, P-1, R2-PF-A1, R2-PF-A2 |
| NFR-4 ▲ | An unchanged frame makes **zero** allocations. Over a one-hour soak the live heap after collection grows by no more than 1 KB a minute (least-squares slope) and the count of goroutines at idle does not change. **A changed frame is the steady state, not the exception** — a blinking marker changes most frames — so it has a pinned test now and provisional numbers, revised only by ruling after the PLAN-exit measurement: Go benchmarks, floor toolchain, the D-48 fixture, 149×38, truecolor, tiles warm. *Provisional, unverified:* a marker-phase change ≤ 16 KB and ≤ 64 allocations; a one-cell pan no more than the first host's own window cost (765 KB, 1,346 allocations); identical counts at 100 and at 1,000 features. | D-29, CQ-14, P-3, R2-PF-A3 |
| NFR-5 ▲ | **Target (D-30):** the placed view within 1 s warm; within 3 s cold **to full detail**; a non-blank frame (FR-23's floor) from the first render call in both cases. Clocked from the host handing in its data; the clock stops at the first full-detail render under a simulated 300 ms host tick. Measured against a local test server **using secure transport**, shaped to a **stated link** — 150 ms round-trip latency, applied to connection setup as well; 8 Mbit/s in aggregate; no more than 6 connections — serving a pinned fixture (the four measured zoom-5 tiles, 1.2 MB). Validated or revised at PLAN exit. | D-30, BQ-5, P-5, R2-PF-A6 |
| NFR-6 ▲ | Render is a pure function of the view, size, colour depth, palette, the time supplied, the overlays and the **ordered set of tiles on hand**. Tiles are visited in a fixed order; nothing depends on map iteration order or on which fetch finished first. Reference frames are byte-identical on amd64 and arm64, **shown by running the reference-frame tests on both** — cross-compiling proves nothing here. Where a product feeds a sum, an explicit conversion prevents the fused multiply-add that arm64 would otherwise apply; non-finite values never reach a float-to-integer step. Results of the standard library's trigonometric, exponential and logarithm functions are not guaranteed identical across architectures (unverified in practice), so projection results are rounded to a stated precision before use; the two-architecture test decides whether that is enough. | AI-4 §9, CQ-11, R2-CQ |
| NFR-7 | macOS, Linux and Windows; UTF-8; usable from a 69×12-cell rectangle; safe over SSH, with nothing that depends on querying the terminal. | D-23 |
| NFR-8 ▲ | Every line of a frame is exactly the requested width under one pinned width table — the same one the first host measures with, **under the fixed narrow condition** (ambiguous-width characters count as one column). Every character the renderer itself emits comes from a closed list checked against the Unicode width data: braille is neutral width, so safe for layout — **but whether fonts carry it is not known, and the terminal cannot be asked (NFR-7)**; block, box-drawing, shade and arrow characters and U+FFFD (which FR-34 emits) are *ambiguous* width. A matrix of supported terminals and fonts, **at PLAN entry**, before any design depends on them, tests both: braille coverage, and the width of every ambiguous glyph (D-57). Text is handled by grapheme cluster (FR-34): a cluster occupies one or two cells by the table, and one that does not fit is dropped whole. *The closed list for v0.1.0 is: space, braille, the marker glyphs, box-drawing for the scale mark, the hatch stroke and severity glyphs (FR-18a), block shades for no-colour images, U+FFFD, and the ASCII letters, digits and punctuation of the library's own text — notice, scale label, value labels, stale mark (D-57).* | AI-3 §6, S2-2, S3-3, CQ-6, A-7, R2-CQ |
| NFR-9 ◆ | Dependencies are an explicit allow-list; each carries a licence file. No `replace` directive in the module file. *The allow-list's contents are a PLAN decision.* | D-13, X-5, S-7 |
| NFR-10 ▲ | **Everything that arrives from outside is untrusted**: compressed bodies, vector tiles, TileJSON, PMTiles headers, directories and metadata, style files, images, and feature input. Limits are **defaults, not proposals** — tests come first, so the numbers are fixed here — enforced **before allocating**, host-settable: tile body ≤ 2 MiB, decompressed ≤ 8 MiB; **per tile, layers ≤ 64, features ≤ 100,000, geometry integers ≤ 2,000,000, retained bytes ≤ 4 MiB, refused over any limit** (checked against real maxima across zoom 0–14 in PLAN; the measured maxima so far cover zoom 0–3 only); PMTiles directory ≤ 1 MiB decompressed, **entry count ≤ the lesser of a quarter of the bytes remaining and 65,536**, leaf depth ≤ 3 with a cycle guard, every offset and length checked for overflow and against the file size; metadata, TileJSON and style ≤ 1 MiB, nesting ≤ 64, reference and constant cycles detected; any other count ≤ the bytes remaining divided by its smallest encoding; tile extent 1..65,536; compression other than none or gzip, and any non-vector tile type, returns a clear "unsupported" error; image limits are FR-9's. | NFR-12 | The library never bulk-downloads or prefetches from the public tile server. | D-21 |
| NFR-13 | MIT licence; both upstream notices carried; OpenMapTiles and OpenStreetMap credited; the embedded data carries its own notice. | D-13, D-25, D-33 |
| NFR-14 ▲ | Sole-author commits; no tool-generated trailers or watermarks. Local development tooling stays untracked. | C-2 (brief), D-7, D-50 |

## Added after red-team round 1 ✚

| ID | Requirement | From |

| **Asynchronous work** | | |
| FR-30 ▲ | **Who runs background work is explicit, bounded and leak-free.** Whatever model PLAN chooses (PLAN proposes at least two, compared in a named design note: host-scheduled blocking calls; a small library-owned pool), it meets all of these: every goroutine has a stated owner and none outlives the map instance (leak-tested); in-flight fetches and the simplification backlog are capped, newest view wins; every job takes a context and is cancelled when its tile or shape leaves the view; one render may run while one fetch runs, shown under the race detector; completion moves the change counter and keeps the next-change deadline (FR-25) current so an idle host still redraws; an optional callback lets a host be told rather than poll. A *settle* call waits for pending work — which is how the headless render (FR-4) produces a complete frame without breaking FR-23 — **and always ends**: it takes a context, returns when nothing is pending or the context ends, and says which, with a count of work that failed — so a headless frame is never silently incomplete; work that failed and is in back-off is not pending. No panic escapes a public call or a library goroutine. | CQ-1, P-2, S-3, R2-CQ |
| FR-31 ✚ | The tile cache never serves a tile parsed for a different style profile or label language: either the key includes them, or tiles are decoded without reference to style. | CQ-8 |

**Safeguard for PLAN:** the contract is designed for all five overlay shapes and built for three, so the deferred shapes constrain the design.

**Checkpoint after the integration (D-60):** before any deferred shape is built, a written integration review goes to HUM LEAD — what the host needed that the contract lacked, memory and timing measured in the real host, contract changes proposed, whether the plan for the rest still holds — and he gives GO.

**What "in PLAN" means in this file.** Each of these is a named PLAN artefact, not a loose promise: the contract document (all five shapes, FR-37's frames, FR-29's data); the asynchronous-model comparison (FR-30); the terminal glyph-width matrix, due at PLAN *entry* (NFR-8); the zoom-bucket definition (FR-11); the default ramps per colour depth with their checker results (FR-16); the semantic-token list for the palette (FR-15, D-63); the pinned fixture (NFR-3); the memory and allocation measurement, due at PLAN *exit* (NFR-3, NFR-4); the dependency allow-list (NFR-9); the per-tile maxima across zoom 0–14 (NFR-10); a confirmed keyless image source for the radar example (NFR-17); the colour-vision threshold (FR-16); the closed list of error kinds (NFR-20); and the owed specimens — the temperature scale with its checker results (D-62), a 16-colour hint (D-59), painted light and dark grounds (D-64), M1 scenarios 2, 6 and 7.
